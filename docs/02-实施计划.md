# AI 招聘多智能体系统实施计划

## 1. 总体顺序

推荐按下面顺序推进：

1. 先确定业务边界和接口契约。
2. 再搭基础设施，让 MySQL、Redis、Milvus 能稳定启动和被服务访问。
3. 然后做 Java 后端，先把招聘流程、数据模型和状态流转跑通。
4. 再做 RAG Service，让简历、岗位和招聘知识能入库、向量化、检索。
5. 再做 Python Agent Runtime，先接 DeepSeek，再实现三个智能体。
6. 最后做邮件、日历、会议适配器，以及日志、指标、审计和端到端验收。

第一阶段不建议直接写三个智能体。原因是智能体依赖岗位、候选人、简历、流程状态、RAG 检索、调用记录等基础能力。如果先写 Agent，后面很容易反复改输入输出结构。

## 2. 第 0 阶段：需求和契约冻结

目标：先明确系统边界，避免一边写代码一边改主流程。

主要工作：

- 明确系统第一版只支持哪些岗位、简历格式、招聘流程状态。
- 明确候选人、岗位、简历、申请记录、分析报告、邮件记录、面试记录的数据字段。
- 明确 Java Backend、Python Agent Runtime、RAG Service 之间的接口。
- 明确 DeepSeek 调用的输入输出格式和失败处理规则。
- 明确哪些动作必须人工确认，例如拒绝候选人、发送邮件、正式安排面试。

产出：

- 本地接口草案。
- 数据模型草案。
- 业务状态流转草案。

验收标准：

- 能清楚说明一次招聘申请从创建到面试安排的完整状态流。
- Java、Python Agent、RAG 三个服务之间的数据边界清楚。
- 没有需要实现阶段再临时决定的核心字段。

## 3. 第 1 阶段：基础设施优先

目标：让依赖环境可启动、可配置、可检查。

优先工作区：

- `infra`
- `mysql`
- `redis`
- `milvus`

已完成：

- 在 `infra` 中落地本地 Docker Compose 启动方案。
- 在 `infra` 中落地 `.env.example`。
- 在 `mysql` 中落地数据库初始化脚本。
- 在 `mysql` 中落地 V1 表结构脚本。
- 在 `mysql` 中落地计算机行业岗位模板种子数据。
- 在 `redis` 中补充 key 命名规范说明。
- 在 `milvus` 中补充 collection 和索引建议说明。

仍需执行：

- 本地启动 Docker Compose。
- 检查 MySQL、Redis、Milvus 健康状态。
- 检查 MySQL 表和岗位模板数据是否初始化成功。
- 检查 Redis 是否返回 `PONG`。
- 检查 Milvus 是否可连接。

原计划工作：

- 在 `infra` 中设计本地启动方案。
- 在 `mysql` 中设计数据库初始化和迁移方案。
- 在 `redis` 中设计缓存、任务状态、幂等锁的 key 命名规范。
- 在 `milvus` 中设计 collection、索引、字段和向量维度策略。
- 准备环境变量规范，但不提交真实密钥。

推荐先做这一部分，因为 Java 后端、RAG 和 Agent 都依赖这些基础组件。

验收标准：

- MySQL、Redis、Milvus 有清晰的本地启动方式。
- 每个组件有健康检查方式。
- 环境变量命名统一。
- 本地数据目录、日志目录、密钥文件不会误提交。

## 4. 第 2 阶段：Java Backend 基础能力

目标：先把招聘业务主流程和数据库状态跑通。

优先工作区：

- `java-backend`
- `mysql`
- `redis`

主要工作：

- 创建 Java 后端基础工程。
- 建立候选人、岗位、简历、申请记录、分析报告、邮件记录、面试记录的数据模型。
- 建立 MySQL schema 和迁移脚本。
- 建立 REST API：
  - 创建岗位。
  - 创建候选人。
  - 提交申请。
  - 查询申请状态。
  - 查询分析结果。
  - 查询邮件和面试记录。
- 建立 Redis 用法：
  - 接口幂等。
  - 任务状态缓存。
  - 简短会话状态。
- 先用 mock Agent 响应打通流程，不急着接 DeepSeek。

为什么第二阶段做 Java：

- Java 后端是系统入口。
- 数据模型和流程状态稳定后，Python Agent 和 RAG 才有稳定输入输出。
- 先做 Java 可以尽早发现业务字段缺失。

验收标准：

- 不接 LLM 的情况下，能创建岗位、候选人、申请记录。
- 申请状态能从“已提交”流转到“等待分析”。
- 数据能正确写入 MySQL。
- Redis 能用于幂等或任务状态。

## 5. 第 3 阶段：RAG Service

目标：让系统具备检索岗位要求、简历片段和招聘知识的能力。

优先工作区：

- `rag-service`
- `milvus`

主要工作：

- 创建 RAG 服务基础工程。
- 设计文档类型：
  - 简历文本。
  - 岗位要求。
  - 招聘知识。
  - 面试题库。
  - 沟通模板。
- 设计文本切分规则。
- 设计 embedding provider 抽象，避免绑定单一向量模型。
- 设计 Milvus collection。
- 提供基础接口：
  - 文档入库。
  - 文档检索。
  - 按岗位检索相关简历证据。
  - 按候选人检索相关岗位证据。
- 先返回可解释的检索结果，不直接让 Agent 使用黑盒上下文。

为什么第三阶段做 RAG：

- 简历分析 Agent 需要 RAG 检索证据。
- 先做 RAG 可以让后续 Agent 输出有依据，而不是只靠模型猜测。
- Milvus 的 collection 设计会影响后续数据结构。

验收标准：

- 能把一段简历或岗位说明切分并写入 Milvus。
- 能通过查询返回相关片段、来源、相似度。
- 检索结果能被 Java Backend 或 Python Agent Runtime 调用。

## 6. 第 4 阶段：Python Agent Runtime 和 DeepSeek

目标：接入 DeepSeek，并实现三个智能体的结构化输出。

优先工作区：

- `python-agent-runtime`
- `rag-service`

主要工作：

- 创建 Python Agent Runtime 基础工程。
- 封装 DeepSeek API Client。
- 统一配置：
  - `DEEPSEEK_API_KEY`
  - `DEEPSEEK_BASE_URL`
  - `DEEPSEEK_MODEL`
- 定义 Agent 输入输出 schema。
- 先实现简历分析 Agent：
  - 输入：候选人简历、岗位要求、RAG 证据。
  - 输出：匹配分数、匹配技能、缺失技能、风险点、推荐动作、人工复核建议。
- 再实现邮件沟通 Agent：
  - 输入：分析结果、候选人状态、邮件类型。
  - 输出：主题、正文、语气、是否需要人工确认。
- 再实现面试安排 Agent：
  - 输入：候选人、岗位、可选时间、面试规则。
  - 输出：候选时间、会议标题、面试说明、需要确认的冲突。

为什么先做简历分析 Agent：

- 简历分析是后续邮件和面试安排的前置条件。
- 邮件内容和面试安排都依赖分析结果。
- 先做好一个 Agent 的输入输出校验，可以复用到另外两个 Agent。

验收标准：

- DeepSeek 调用封装不泄露密钥。
- Agent 输出必须是结构化数据。
- 模型返回异常或格式错误时有明确失败结果。
- 简历分析 Agent 能结合 RAG 证据输出分析结果。

## 7. 第 5 阶段：Java 与 Agent 集成

目标：让 Java 后端能真正调用 Python Agent Runtime，完成简历分析流程。

优先工作区：

- `java-backend`
- `python-agent-runtime`
- `rag-service`

主要工作：

- Java Backend 调用 Python Agent Runtime。
- Python Agent Runtime 调用 RAG Service。
- RAG Service 返回检索证据。
- Python Agent Runtime 调用 DeepSeek 生成分析结果。
- Java Backend 保存分析结果和 Agent 调用记录。
- 增加状态流转：
  - 已提交。
  - 等待分析。
  - 分析中。
  - 待人工复核。
  - 分析完成。
  - 分析失败。

验收标准：

- 一条申请能触发简历分析。
- 分析过程有状态记录。
- 分析失败能重试或人工介入。
- MySQL 中能查到分析结果和调用审计记录。

## 8. 第 6 阶段：邮件沟通能力

目标：先生成邮件草稿，再考虑真实发送。

优先工作区：

- `python-agent-runtime`
- `java-backend`

主要工作：

- 实现邮件沟通 Agent。
- Java Backend 提供邮件草稿查询、确认、发送状态接口。
- 定义 Email Provider Adapter。
- 第一版建议只生成邮件草稿，不直接发送。
- 人工确认后再调用具体邮件供应商。

为什么不一开始真实发送：

- 邮件属于对外动作，错误成本高。
- 招聘拒信、面试邀请都需要人工审核语气和内容。
- 先做草稿可以更安全地验证 Agent 质量。

验收标准：

- 根据分析结果生成邮件草稿。
- 邮件草稿能保存到 MySQL。
- 邮件发送前有人工确认状态。
- 邮件供应商仍然通过适配器接入，不绑定具体平台。

## 9. 第 7 阶段：面试安排能力

目标：先生成面试安排建议，再接入真实日历和会议系统。

优先工作区：

- `python-agent-runtime`
- `java-backend`

主要工作：

- 实现面试安排 Agent。
- 定义 Calendar Provider Adapter。
- 定义 Meeting Provider Adapter。
- Java Backend 保存面试安排记录。
- 第一版先生成面试建议，不直接创建真实会议。
- 人工确认后再创建日历事件和会议链接。

验收标准：

- 能根据候选人、岗位和可用时间生成面试安排建议。
- 面试安排能保存到 MySQL。
- 能区分“建议中”“待确认”“已安排”“已取消”“改期中”等状态。
- 日历和会议供应商没有被硬编码到 Agent 逻辑中。

## 10. 第 8 阶段：可观测性和审计

目标：让系统可排查、可追踪、可复盘。

优先工作区：

- `observability`
- `java-backend`
- `python-agent-runtime`
- `rag-service`

主要工作：

- 设计统一 trace id。
- 记录每次 Agent 调用：
  - 输入摘要。
  - 输出摘要。
  - DeepSeek 模型。
  - 调用耗时。
  - token 用量。
  - 成功或失败原因。
- 记录 RAG 检索：
  - 查询文本。
  - 返回片段。
  - 相似度。
  - 命中文档来源。
- 设计基础指标：
  - 简历分析成功率。
  - DeepSeek 调用失败率。
  - RAG 检索耗时。
  - 邮件草稿生成耗时。
  - 面试安排生成耗时。

验收标准：

- 一次申请流程可以从 Java Backend 追踪到 Python Agent 和 RAG Service。
- 失败原因可定位。
- 能统计 DeepSeek 调用成本和失败率。

## 11. 第 9 阶段：端到端验收

目标：把整个招聘流程串起来。

主要流程：

1. 创建岗位。
2. 创建候选人。
3. 提交简历。
4. 简历和岗位知识进入 RAG。
5. 触发简历分析 Agent。
6. 保存分析报告。
7. 生成邮件草稿。
8. 如果候选人通过筛选，生成面试安排建议。
9. 人工确认后标记邮件和面试状态。

验收标准：

- 从候选人提交申请到生成分析报告可以完整跑通。
- 邮件和面试安排默认不直接对外发送，必须人工确认。
- 所有关键状态能在 MySQL 中查询。
- Agent 调用、RAG 检索、DeepSeek 调用都有审计记录。
