# 基础设施设计

## 1. 文档目标

本文定义 V1 本地开发环境中 `infra`、`mysql`、`redis`、`milvus` 四个工作区的职责、启动方式、端口规划、环境变量、健康检查和数据目录策略。

本文件最初用于基础设施设计；当前已根据该设计落地基础设施配置和 MySQL 初始化脚本。

## 2. 基础设施范围

V1 本地基础设施包含：

```text
MySQL
Redis
Milvus
```

它们服务于：

```text
frontend/admin
java-backend
python-agent-runtime
rag-service
```

职责关系：

```text
Java Backend
  -> MySQL: 业务数据
  -> Redis: 任务状态、幂等锁、缓存
  -> Python Agent Runtime: Agent 编排

Python Agent Runtime
  -> DeepSeek API: 模型调用
  -> RAG Service: 检索证据

RAG Service
  -> Milvus: 向量检索
  -> MySQL: 可选，读取或记录 RAG 文档元数据
```

## 3. 工作区职责

### 3.1 `infra`

`infra` 是本地基础设施编排工作区。

后续应放置：

- `docker-compose.yml`
- `.env.example`
- 本地启动脚本。
- 本地停止脚本。
- 健康检查脚本。
- 服务端口说明。
- 本地数据目录说明。

`infra` 不放业务代码。

### 3.2 `mysql`

`mysql` 是数据库结构和初始化工作区。

后续应放置：

- MySQL 初始化脚本。
- 数据库迁移脚本。
- 初始岗位模板数据。
- 数据库设计补充说明。

`mysql` 不保存真实业务数据文件。

### 3.3 `redis`

`redis` 是缓存、任务状态和 key 规范工作区。

后续应放置：

- Redis key 命名规范。

- 本地 Redis 配置说明。

`redis` 不保存本地 Redis 持久化数据。

### 3.4 `milvus`

`milvus` 是向量库集合、索引和检索规范工作区。

后续应放置：

- Milvus collection 设计。
- 向量字段设计。
- 索引类型说明。
- 检索过滤字段说明。
- 本地 Milvus 配置说明。

`milvus` 不保存本地向量库数据文件。

## 4. 本地启动方案

建议 V1 使用 Docker Compose 启动基础设施。

理由：

- MySQL、Redis、Milvus 都适合容器化启动。
- 本地开发环境一致性更高。
- 后续 Java Backend、RAG Service 和 Python Agent Runtime 可以共享同一套连接配置。
- 健康检查可以统一放在 Compose 或脚本里。

当前 `infra/docker-compose.yml` 已包含：

```text
mysql
redis
milvus
etcd
minio
```

说明：

- Milvus Standalone 通常需要 `etcd` 和 `minio` 作为依赖。
- `etcd` 用于 Milvus 元数据。
- `minio` 用于 Milvus 对象存储。
- 这些依赖对业务服务透明，由 `infra` 统一编排。

## 5. 端口规划

建议本地端口：

| 服务 | 容器端口 | 本地端口 | 说明 |
| --- | --- | --- | --- |
| MySQL | 3306 | 3306 | 业务数据库 |
| Redis | 6379 | 6379 | 缓存和任务状态 |
| Milvus | 19530 | 19530 | Milvus gRPC |
| Milvus | 9091 | 9091 | Milvus HTTP/metrics |
| etcd | 2379 | 2379 | Milvus 依赖 |
| MinIO API | 9000 | 9000 | Milvus 依赖 |
| MinIO Console | 9001 | 9001 | 本地调试 |

后续业务服务建议端口：

| 服务 | 本地端口 | 说明 |
| --- | --- | --- |
| frontend/admin | 3000 | 管理端前端 |
| java-backend | 8080 | 主业务 API |
| python-agent-runtime | 8100 | Agent 内部服务 |
| rag-service | 8200 | RAG 内部服务 |

如果端口被占用，优先改业务服务端口，不优先改基础组件端口。

## 7. MySQL 设计

### 7.1 数据库

建议数据库名：

```text
ai_recruitment
```

建议本地用户：

```text
ai_recruitment
```

### 7.2 初始化顺序

当前初始化脚本：

```text
create-database.sql
create-tables.sql
seed-job-templates.sql
```

说明：

- `create-database.sql` 创建数据库和基础字符集。
- `create-tables.sql` 创建接口契约中冻结的表。
- `seed-job-templates.sql` 写入计算机行业常见岗位模板。
- MySQL 容器初始化脚本会按文件名字母顺序执行。当前依赖关系为：先创建数据库，再创建表，再写入岗位模板。

### 7.3 字符集

建议：

```text
utf8mb4
utf8mb4_unicode_ci
```

理由：

- 支持中文、英文和特殊符号。
- 简历文本、岗位描述、邮件草稿都可能包含多语言内容。

### 7.4 健康检查

MySQL 健康检查建议：

```text
mysqladmin ping
```

或：

```sql
SELECT 1;
```

健康标准：

- 容器运行中。
- 端口可连接。
- `SELECT 1` 成功。
- 数据库 `ai_recruitment` 存在。

## 8. Redis 设计

### 8.1 使用场景

V1 Redis 用于：

- 幂等锁。
- Agent 任务状态。
- RAG 检索短期缓存。
- DeepSeek 调用短期缓存。
- 接口限流计数。

### 8.2 Key 命名规范

建议统一格式：

```text
ai-recruitment:{domain}:{type}:{id}
```

示例：

```text
ai-recruitment:application:lock:{applicationId}
ai-recruitment:agent-run:status:{agentRunId}
ai-recruitment:rag:search-cache:{hash}
ai-recruitment:rate-limit:user:{userId}
```

### 8.3 TTL 规范

建议：

| 场景 | TTL |
| --- | --- |
| 幂等锁 | 5-30 分钟 |
| Agent 任务状态 | 24 小时 |
| RAG 检索缓存 | 10-60 分钟 |
| DeepSeek 短期缓存 | 10-60 分钟 |
| 限流计数 | 1-60 分钟 |

### 8.4 健康检查

Redis 健康检查建议：

```text
redis-cli ping
```

健康标准：

```text
PONG
```

## 9. Milvus 设计

### 9.1 部署模式

V1 本地建议使用 Milvus Standalone。

理由：

- 本地开发成本低。
- 足够支持简历、岗位、招聘知识和模板检索。
- 后续如数据量变大，可升级到集群模式。

### 9.2 Collection 设计

建议 V1 使用一个统一 collection：

```text
recruitment_knowledge_chunks
```

理由：

- 简历片段、岗位要求、招聘知识、邮件模板都可以抽象为 chunk。
- 通过 `source_type`、`source_id`、`application_id`、`job_position_id` 过滤。
- V1 不需要一开始拆多个 collection，避免检索逻辑复杂。

### 9.3 字段设计

建议字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | varchar | chunk ID |
| source_type | varchar | RESUME / JOB_REQUIREMENT / KNOWLEDGE / TEMPLATE |
| source_id | varchar | 来源业务 ID |
| application_id | varchar | 申请 ID，可为空 |
| job_position_id | varchar | 岗位 ID，可为空 |
| chunk_index | int | 分片序号 |
| content | varchar | 文本片段 |
| embedding | float vector | 向量 |
| metadata_json | varchar | 元数据 |
| created_at | varchar | 创建时间 |

### 9.4 向量维度

向量维度取决于后续选择的 embedding 模型。

当前冻结原则：

- 不在本阶段写死具体维度。
- 在 RAG Service 实现时由 embedding provider 配置决定。
- Milvus collection 创建时必须读取统一配置，避免模型维度和 collection 维度不一致。

### 9.5 索引建议

V1 建议：

```text
index_type: HNSW
metric_type: COSINE
```

理由：

- HNSW 适合中小规模本地检索。
- COSINE 适合大多数文本 embedding 相似度。

如果后续数据量较大，可评估 IVF_FLAT 或其他索引。

### 9.6 健康检查

Milvus 健康检查建议：

- gRPC 端口 `19530` 可连接。
- HTTP/metrics 端口 `9091` 可访问。
- RAG Service 能成功创建测试 collection 或列出 collection。

健康标准：

```text
Milvus 服务可连接
collection 操作成功
向量写入和检索 smoke test 成功
```

## 10. 本地数据目录策略

建议后续本地数据放在：

```text
infra/data/mysql
infra/data/redis
infra/data/milvus
infra/data/etcd
infra/data/minio
```

这些目录必须被 `.gitignore` 排除。

原因：

- 本地数据库文件不应提交。
- Milvus 向量数据可能很大。
- MinIO/etcd 数据属于运行时状态。

## 12. 启动顺序

建议本地启动顺序：

```text
1. MySQL
2. Redis
3. etcd
4. MinIO
5. Milvus
6. rag-service
7. python-agent-runtime
8. java-backend
9. frontend/admin
```

说明：

- RAG Service 依赖 Milvus。
- Python Agent Runtime 依赖 RAG Service 和 DeepSeek 配置。
- Java Backend 依赖 MySQL、Redis、RAG Service、Python Agent Runtime。
- Frontend 依赖 Java Backend。

## 13. 验收标准

基础设施阶段完成后，应满足：

- 能一键启动 MySQL、Redis、Milvus 及其依赖。
- 能通过健康检查确认 MySQL 可连接。
- 能通过健康检查确认 Redis 可连接。
- 能通过健康检查确认 Milvus 可连接。
- `.env.example` 明确列出本地开发所需环境变量。
- 本地数据目录不会被 Git 提交。
- Java Backend、RAG Service、Python Agent Runtime 能使用同一套环境变量连接基础设施。
